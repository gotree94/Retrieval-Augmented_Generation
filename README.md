## 1. RAG (Retrieval-Augmented Generation)

### 1.1 정의
LLM이 답변을 생성하기 전에 외부 자료에서 관련 내용을 먼저 검색해 프롬프트에 함께 넣어 주는 방식. "시험 볼 때 교재를 펴놓고 보게 하는" 구조.

### 1.2 왜 필요한가
- LLM은 학습 시점까지의 지식만 가짐 (내부 문서, 최신 정보 모름)
- 모르는 내용을 그럴듯하게 지어내는 환각(hallucination) 문제
- 파인튜닝은 비용이 크고 지식 갱신이 번거로움

### 1.3 동작 흐름

**사전 준비(인덱싱)**
1. 문서(PDF, 데이터시트, 매뉴얼 등)를 청크(chunk)로 분할
2. 임베딩 모델로 각 청크를 벡터화
3. 벡터 DB(FAISS, Chroma, Qdrant, pgvector 등)에 저장

**질의 시(검색 + 생성)**
1. 질문을 같은 임베딩 모델로 벡터화
2. 벡터 DB에서 가까운 청크 top-k 검색
3. [질문 + 검색된 청크]를 LLM에 전달
4. LLM이 근거 기반으로 답변

```
질문 → 임베딩 → 벡터 검색 → 관련 청크 → [질문 + 청크] → LLM → 답변
```

### 1.4 RAG vs 파인튜닝

| 구분 | RAG | 파인튜닝 |
|---|---|---|
| 지식 갱신 | 문서만 교체 | 재학습 필요 |
| 출처 제시 | 가능 | 어려움 |
| 비용 | 낮음 | 높음 |
| 적합한 용도 | 사실·문서 기반 질의응답 | 말투, 형식, 작업 스타일 학습 |

둘은 대체 관계가 아니며 함께 쓸 수 있다.

### 1.5 품질을 좌우하는 요소
- **청킹 전략**: 너무 작으면 맥락 단절, 너무 크면 검색 정확도 저하
- **임베딩 모델**: 한국어 문서는 다국어/한국어 성능이 좋은 모델 선택
- **검색 방식**: 벡터 + 키워드(BM25) 하이브리드, 리랭커(reranker)
- **프롬프트 설계**: "제공된 문서에 없으면 모른다고 답하라" 등 환각 억제 지시

### 1.6 한계
- 검색이 엉뚱한 청크를 가져오면 답도 틀어짐
- 표, 회로도, 그림이 많은 문서는 텍스트 추출 품질이 병목
- 여러 문서를 종합해야 하는 질문은 단순 top-k로 어려움

## 2. opencode에서 RAG 사용하기

### 2.1 결론
검색한 범위에서는 opencode에 RAG가 내장된 것으로 확인되지 않았다(내장 여부는 공식 문서로 재확인 필요). 대신 **MCP(Model Context Protocol) 서버를 설정 파일의 `mcp` 항목에 등록**해 RAG 기능을 붙이는 방식이 일반적이다.

### 2.2 확인된 MCP 기반 사례
| 도구 | 성격 | 특징 |
|---|---|---|
| Semble | 로컬 코드 검색 | CPU 동작, API 키 불필요, `uvx`로 실행 |
| codebase-search-4-agents | 코드 RAG 예제 | pgvector + sentence-transformers + MCP Python SDK. 직접 구성 학습용으로 적합 |
| CodebaseAgent-MCP | 저장소 분석 위임 | 가벼운 RAG로 저장소 분석을 별도 LLM에 맡기고 결과만 전달 |
| GitNexus, LeanKG | 지식 그래프 기반 | 벡터 RAG가 아닌 의존성/호출 관계 그래프. opencode 연동 지원 |

### 2.3 코드가 아닌 문서 RAG
- Qdrant + Ollama/OpenAI 임베딩 기반의 문서 검색 MCP 서버를 쓰거나
- Python MCP SDK로 `search_docs(query)` 도구 하나를 직접 만들어 등록

### 2.4 RAG 없이도 충분한 경우
opencode는 grep, 파일 읽기로 코드를 탐색하는 에이전트형 구조. 소규모 프로젝트는 RAG 없이 충분하며, 저장소가 매우 크거나 이름이 달라도 의미가 유사한 코드를 찾아야 할 때 RAG 이점이 커진다.

## 3. RAG 오픈소스 환경

### 3.1 완성형 앱 (설치 후 문서만 투입)
| 도구 | 성격 | 메모 |
|---|---|---|
| Open WebUI | 셀프호스팅 채팅 UI | Ollama/OpenAI 호환 API 연동, RAG·벡터DB·RBAC 지원. 채팅 인터페이스 중심(앱 개발 플랫폼은 아님) |
| AnythingLLM | 올인원 RAG 앱(데스크톱/Docker) | 문서 수집~검색 전체 파이프라인 처리. 입문용으로 가장 간단 |
| RAGFlow | 문서 중심 RAG | 깊은 문서 파싱에 강점. 표·복잡한 레이아웃 PDF에 적합 |
| Dify | LLM 앱 개발 플랫폼 | 워크플로 + RAG + 에이전트. 복잡도 높음, Docker Compose 다중 서비스. 멀티테넌트 상용 SaaS는 라이선스 제한 확인 필요 |
| Onyx(구 Danswer) | 기업용 검색 + RAG | 여러 문서 소스 연결, 팀 환경 |

### 3.2 라이브러리 (코드로 직접 구성)
| 도구 | 적합한 용도 |
|---|---|
| LlamaIndex | 문서 질의응답 중심, 입문 코드 구성에 무난 |
| LangChain | 에이전트 + 여러 도구 연동 복잡 앱 |
| Haystack | 모듈식 검색 파이프라인, 프로덕션 지향 |
| txtai | 검색 중심 제품 |

### 3.3 벡터 DB
- 시작: **Chroma** (파이썬에 내장 가능, 서버 실행도 가능)
- 확장: Qdrant, Milvus, pgvector

### 3.4 추천 시작 경로
1. 빠른 체험: Ollama + Open WebUI(또는 AnythingLLM)에 PDF 몇 개 올려 질문
2. 구조 이해: 파이썬 + LlamaIndex + Chroma + Ollama로 최소 예제 작성
3. 복잡한 PDF: RAGFlow를 Docker로 띄워 파싱 품질 비교

## 4. 이미지 생성 모델의 파인튜닝

### 4.1 가능한가
가능하다. 가중치가 공개된 오픈소스 이미지 모델(Stable Diffusion 계열, FLUX 계열 등)은 자기 데이터로 추가 학습할 수 있으며, 전체 재학습보다 경량 방식을 주로 쓴다.

### 4.2 방식 비교
| 방식 | 용도 | 필요 데이터 |
|---|---|---|
| LoRA | 화풍, 캐릭터, 제품 스타일 (가장 많이 사용) | 수십 장 |
| DreamBooth | 특정 인물/사물/브랜드 제품 주입 | 5~30장 |
| Textual Inversion | 새 개념을 토큰 하나로 학습 (가볍지만 표현력 낮음) | 소량 |
| 풀 파인튜닝 | 모델 전체 조정 | 대량 + 고사양 GPU |

### 4.3 학습 도구
Hugging Face diffusers(공식 학습 스크립트), kohya_ss, OneTrainer, ai-toolkit, SimpleTuner.

### 4.4 텍스트 RAG와의 관계
이미지 모델에는 "검색해서 프롬프트에 붙이는" 구조가 그대로 있지 않다. 대신 유사 방법이 있다.
- **참조 이미지 조건화**: IP-Adapter, ControlNet. 벡터 DB에서 유사 이미지를 검색해 참조로 넘기면 사실상 이미지 RAG
- **연구 단계**: Retrieval-Augmented Diffusion 계열 (실무 도구로는 덜 정착)
- **프롬프트 단 RAG**: 텍스트 RAG로 사양/스타일 가이드를 찾아 이미지 프롬프트를 자동 구성

### 4.5 내 스타일/프로젝트 스타일로 파인튜닝 가능한가
**가능하며 가장 흔한 활용 방식**이다.

잘 되는 것
- 개인 화풍, 드로잉 스타일 (20~50장 LoRA)
- 프로젝트 고유 룩앤필(브랜드 톤, 제품 라인 렌더링 스타일)
- 특정 제품/소품 외형 주입 (DreamBooth 계열)
- 스케치 → 결과물 (LoRA + ControlNet)

한계
- **치수·구조의 정확성 보장 불가**: 설계 도면이 아니라 시안/시각 자료용
- 로고, 글자, 작은 부품 디테일은 후보정 필요
- 데이터 품질이 결과를 좌우 (일관성, 캡션, 다양성)
- 과적합 위험 (학습 이미지 재현만 하는 현상)
- **라이선스**: 베이스 모델별 상업 이용 조건이 다르며, 학습 이미지의 저작권도 정리 필요

### 4.6 권장 구성

| 단계 | 선택 | 이유 |
|---|---|---|
| 베이스 모델 | SDXL 계열(안정성, 생태계, 낮은 VRAM) 또는 FLUX 계열(품질 우선) | SDXL은 LoRA/ControlNet 자료 풍부 |
| 스타일 학습 | LoRA (rank 16~32에서 시작) | 20~50장 가능, 파일이 작아 프로젝트별 교체 가능 |
| 학습 도구 | ai-toolkit / kohya_ss / OneTrainer | FLUX는 ai-toolkit, SDXL은 kohya_ss/OneTrainer가 많이 쓰임 |
| 구조 제어 | ControlNet (스케치, 윤곽선, 깊이) | 형태는 내가, 스타일은 모델이 |
| 참조 활용 | IP-Adapter | 학습 없이 참조 한 장의 분위기 차용 |
| 실행 환경 | ComfyUI | 워크플로 저장/재사용, 프로젝트 단위 관리 |

### 4.7 학습 데이터 준비 원칙 (결과의 큰 비중)
- 양: 스타일 20~50장, 특정 사물 10~30장
- 일관성: 스타일이 섞이지 않게 선별 (대표작 위주)
- 다양성: 같은 스타일 안에서 구도·피사체·조명 다양화
- 캡션: 자동 캡셔닝 후 직접 수정. 내용 위주로 묘사
- 해상도: 베이스 모델 권장 해상도에 맞춰 크롭/리사이즈

### 4.8 학습 후 검증
1. 체크포인트를 중간중간 여러 개 저장
2. 같은 프롬프트·시드로 체크포인트 비교
3. 학습에 없던 새 주제로도 스타일 유지되는지 확인 (과적합 판별)
4. LoRA 강도(0.6~1.0) 조절

## 5. 영상 생성 모델

### 5.1 이미지와의 차이
- **시간 축 추가**: 프레임 간 움직임, 물체의 일관성
- **연산 비용 큼**: VRAM, 생성/학습 시간이 이미지와 비교 불가. 보통 몇 초 단위 클립을 이어 붙임
- **데이터 준비가 무거움**: 짧은 영상 클립 + 클립별 캡션
- **세대 교체가 빠름**: 최선의 모델이 수개월 단위로 바뀜

### 5.2 오픈소스 계열 (참고)
Wan, HunyuanVideo, LTX-Video, CogVideoX 등이 알려져 있고 ComfyUI에서 실행하는 경우가 많다. 현재 최신 모델·기능·라이선스는 미확인이므로 공식 저장소 확인 필수.

### 5.3 파인튜닝
이미지와 같은 LoRA 방식이 영상 모델에도 쓰인다.
- 스타일 LoRA (이미지 데이터만으로도, 영상 클립으로도 가능)
- 캐릭터/사물 LoRA
- 움직임(카메라 워크, 동작 패턴) LoRA

학습 도구는 모델별로 다르다 (diffusers 계열 스크립트, musubi-tuner, DiffSynth 등이 거론됨).

### 5.4 현실적 접근: 이미지 파이프라인 재활용
1. 내 이미지 LoRA로 **키프레임 이미지** 생성 (스타일은 여기서 확정)
2. **이미지 → 영상(I2V)** 모델로 움직임 부여
3. 시작/끝 프레임 지정 보간, 클립 이어 붙이기로 길이 확장

영상 모델 자체 파인튜닝보다 비용이 적고 일관성 관리가 쉽다.

### 5.5 한계
- 긴 영상에서 인물/사물이 변하는 문제
- 정확한 동작·물리 정합성 보장 안 됨 (시안/시각 자료용)
- 하드웨어 요구량이 높아 해상도·길이가 제한됨
